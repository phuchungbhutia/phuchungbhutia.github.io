Building an Automated, Serverless MLBB Meta Hub on GitHub Pages

Gaming wikis are notoriously frustrating to use. Between intrusive banner ads, bloated tracking scripts, and outdated community builds that haven’t been touched in three patches, finding exact item-by-item interaction logic is a chore.

I set out to build an alternative: a clean, deterministic, zero-bloat game database for Mobile Legends: Bang Bang (MLBB) running on Original Server Patch 2.1.95a. The entire system is open-source, version-controlled, and hosted for free on GitHub Pages without maintaining an expensive backend database.

Here is the complete walkthrough of how the architecture works, how the pipeline bridges raw Markdown to real-time search, the real-world deployment bugs encountered, and how we solved them.

The Architectural Blueprint#

Instead of a traditional SQL database or headless CMS, the project uses Markdown as the single source of truth.

Markdown Master Files (MLBB_Hero_Database.md, MLBB_Game_Data.md)
│
▼
scripts/parse-markdown.mjs
│
▼
Structured JSON Datasets (data/*.json)
│
▼
VitePress Build-Time Data Loaders
│
▼
Vue Component Layer (Instant Search & Meta Filtering)
│
▼
GitHub Actions Deployment CDN

This design gives us three distinct advantages:

  1. Full Transparency: Any player can inspect changes via Git commits or verify mechanical adjustments using standard pull requests.
  2. Deterministic Schemas: Automation scripts extract data into machine-readable JSON for external RAG pipelines, bots, and tools.
  3. Zero Hosting Overhead: The site compiles to static HTML, JavaScript, and CSS served globally on GitHub’s CDN.

Phase 1: Structuring the Data#

The system relies on two human-readable data books:

  • MLBB_Hero_Database.md: Houses the master index of over 100+ heroes, categorizing roles, lanes, combat archetypes, stat scaling curves, tiers, win/ban rates, and deep profile kits.
  • MLBB_Game_Data.md: Houses complete equipment indexes, passive trigger conditions, emblem talent matrices, battle spells, and live patch tracking notes.

To keep data maintainable at scale, a custom generator script (scripts/populate-all-heroes.mjs) builds out the roster systematically, while a zero-dependency parser (scripts/parse-markdown.mjs) reads the Markdown tables and hero kit blocks using regular expressions. The parser maps equipment lists, spells, and emblem paths directly to each hero before outputting clean JSON files into data/heroes.json, data/equipment.json, and data/spells.json.

Phase 2: Building the Reactive Explorer#

Static tables can be long and cumbersome to navigate on mobile devices. To make the database usable during ranked drafts, we created the Interactive Meta Explorer.

Instead of fetching JSON across the network at runtime, VitePress utilizes build-time data loaders (docs/heroes.data.mjs):

import fs from 'node:fs'
import path from 'node:path'

export default {
  watch: ['../data/heroes.json'],
  load() {
    const filePath = path.resolve(process.cwd(), 'data/heroes.json')
    if (!fs.existsSync(filePath)) return []
    return JSON.parse(fs.readFileSync(filePath, 'utf-8'))
  }
}

The data loader injects the parsed dataset directly into a Vue component (HeroExplorer.vue) during site generation. The component provides:

  • Instant client-side text filtering across hero names, lanes, and combat archetypes.
  • Live item search (e.g., querying “War Axe” or “Flicker” highlights every hero utilizing that specific gear).
  • Dropdown role filtering for swift draft comparisons.
  • Compact visual badges for tiers, battle spells, and emblem loadouts.

Phase 3: The In-Browser Contribution Engine#

Static documentation sites usually require pulling a Git branch locally, editing files in an IDE, and running build scripts to push an update. To allow quick updates from any browser, we implemented an in-browser database editor (docs/update-database.md).

Using a client-side component (DatabaseEditor.vue) backed by the GitHub REST API:

  1. An authorized maintainer enters a GitHub Personal Access Token along with updated hero stats or gear changes.
  2. The component retrieves the latest MLBB_Hero_Database.md from the repository via API.
  3. It parses the Markdown string, injects the new hero into the master table, appends the detailed kit build profile, and commits the updated file directly to the main branch.
  4. The API commit triggers the automated CI/CD pipeline, rebuilding the production bundle and publishing the changes live within 60 seconds.

Battle-Tested Troubleshooting: Solving Real-World Breakages#

Developing this project locally on Windows with VSCodium and deploying to GitHub Pages exposed several edge cases. We documented every failure and fix inside TROUBLESHOOTING.md.

1. The Persistent GitHub Pages 404 (Legacy Branch Lock)#

  • Symptom: GitHub Actions passed with green checkmarks, but visiting the live URL returned a GitHub 404 page.
  • Root Cause: Inspecting the repository via the GitHub CLI (gh api repos/.../pages) revealed that GitHub Pages was still bound to the legacy configuration reading from the root of master. Because our repository was working on main and deploying static artifacts via Actions, Pages ignored the compiled build.
  • Fix: We deleted the stale master branch, updated the repository’s default branch to main, and re-pointed the Pages build engine to use the workflow deployment target:
gh api -X PUT repos/phuchungbhutia/mlbb-database/pages -f build_type=workflow

2. Raw YAML Frontmatter Rendering#

  • Symptom: The home page rendered literal text strings (layout: home hero: ...) on screen instead of the formatted VitePress banner.
  • Root Cause: VitePress strictly requires the opening triple hyphens (---) to reside on line 1, column 1. An empty leading line caused the Markdown compiler to interpret the metadata as standard body text.
  • Fix: Normalized docs/index.md ensuring strict UTF-8 formatting and immediate delimiter positioning.

3. Vue SFC Parser Errors in Markdown#

  • Symptom: VitePress failed to compile with [plugin:vite:vue] Element is missing end tag.
  • Root Cause: Embedding extensive Vue template directives, emojis, and inline HTML tables directly inside a .md file confused the Markdown-it AST parser.
  • Fix: Decoupled the logic completely by writing the table as a clean Vue Single File Component (HeroExplorer.vue) and mounting the custom component cleanly inside docs/explorer.md.

4. Missing Build Items in Summary Tables#

  • Symptom: The explorer displayed hero rows, but all item columns fell back to "Standard Build".
  • Root Cause: The parser script was originally reading only the top-level index table, which lacked gear columns.
  • Fix: Enhanced scripts/parse-markdown.mjs to traverse both the index table and individual profile headers (### X. HeroName), extracting items, battle spells, and emblem strings into unified JSON objects.

Verification and Continuous Deployment#

The repository is guarded by an automated GitHub Actions pipeline (deploy-pages.yml):

name: Deploy VitePress to GitHub Pages

on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run parse
      - run: npm test
      - run: npm run docs:build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: docs/.vitepress/dist

  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    needs: build
    runs-on: ubuntu-latest
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4

On every commit, dependencies are cleanly resolved via npm ci, tables are verified against schema tests, VitePress compiles static assets, and the site deploys seamlessly to the edge CDN.

Conclusion#

By treating game analytics like clean code—pairing human-readable Markdown with deterministic parsing and static site tooling—we achieved a fast, searchable, and community-maintainable meta hub.
