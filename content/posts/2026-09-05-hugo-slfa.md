Maintaining public-sector web portals comes with a unique set of constraints. Reliability isn’t a nice-to-have; it is the entire requirement. When circulars, compliance directives, and statutory notifications need to reach regional auditors and administrative officers, the publishing pipeline cannot stall because of Ruby dependency shifts or YAML parser quirks.

For years, the Sikkim Local Fund Audit portal relied on the Jekyll framework paired with the Chirpy theme. While functional in its early days, the platform gradually turned into a maintenance bottleneck.

Here is why we decided to completely scrap the Ruby runtime, rebuild the platform around the Hugo Extended engine and PaperMod, and automate the ingestion pipeline.

---

### The Breaking Point: Why Jekyll Fell Short

Jekyll is the classic choice for GitHub Pages, but as our repository grew, subtle pain points accumulated:

1. **The Fragile Local Environment:** Running Jekyll locally on Windows requires a full Ruby development kit, native C extensions (`msys2`), and Bundler. A single minor version change in a remote gem frequently broke local developer machines.
2. **The "Two-Category" Chirpy Lock:** Jekyll's Chirpy theme enforces a rigid two-tier taxonomy hierarchy (`categories: [Parent, Child]`). Introducing multi-tiered institutional categorizations or flat administrative tags repeatedly caused layout generation to fail.
3. **Escaped Liquid & Front Matter Sensitivity:** A stray unquoted colon in a notice title like `title: Notice: Audit Submission` or an uneven timestamp format would abort the entire Jekyll parser during deployment.
4. **Sluggish Build Times:** Every minor textual correction took 4 to 6 minutes to compile and propagate through GitHub's standard build worker.

It became obvious that our team needed a system compiled into a single, self-contained executable with zero dynamic dependencies. Hugo was the obvious replacement.

### Architectural Upgrades: Jekyll vs. Hugo PaperMod

| Capability | Legacy (Jekyll + Chirpy) | Modern (Hugo + PaperMod) |
| :--- | :--- | :--- |
| **Runtime Core** | Ruby + Bundler Gems | Self-contained Go Binary |
| **Local Windows Setup** | Complex (`RubyInstaller`, MSYS2) | One line (`winget install Hugo.Hugo.Extended`) |
| **Taxonomy Freedom** | Hard limit of 2 nested categories | Unlimited tags and multidimensional categories |
| **Compile Benchmark** | 240 – 360 seconds | **0.04 seconds** locally; ~18s in GitHub Actions |
| **Pages Deployment** | Branch-based git commit pushing | Native GitHub Actions artifact deployment |
| **Client-Side Search** | Heavy dynamic index | Lightweight, instant Fuse.js client search |

### Key Architectural Overhauls

#### 1. Transitioning to Direct GitHub Actions Artifacts
Historically, Jekyll pushed compiled HTML back into a separate `gh-pages` branch. This approach clutters git history and occasionally causes race conditions. 

We switched GitHub Pages deployment source to **GitHub Actions**. The pipeline now compiles the site in an isolated Ubuntu runner and uploads the generated `public/` directory straight to the Pages CDN edge via `actions/upload-pages-artifact` and `actions/deploy-pages`.

#### 2. The Pre-Build In-Runner Sanitizer
To prevent misformatted Markdown submissions from breaking production, we introduced a pre-build Python step directly within `.github/workflows/hugo.yaml`.

This step runs in-memory on every pull request or push:
* Strips legacy Kramdown tags (`{: .prompt-info }`) and Chirpy-specific Liquid syntax.
* Fixes unquoted YAML colons in titles.
* Normalizes publication timestamps to ISO 8601 standard (`YYYY-MM-DDTHH:MM:SS+05:30`).
* Maps Chirpy's legacy cover image block format to PaperMod's native `cover` schema.

#### 3. Zero-Maintenance Document Management via Cloud Shortcodes

State circulars, finance acts, and statutory rules exist as bulky PDF files. Rather than committing multi-megabyte binaries into Git, we authored a custom Hugo shortcode:

```html
{{</* gdrive-folder id="1WFikN4k7GVZCjR5VYlYk1IJ6d5v1oJqd" title="Official Records" */>}}

```

This shortcode wraps the official Google Drive repository into a clean, lazy-loaded frame with direct external access links. Administrative officers can drop fresh audit circulars into Drive from their desktops, and the public portal reflects the new files instantly without requiring a code commit or CI rebuild.

---

### Results and Observations

The migration delivered immediate operational improvements:

* **Near-instant local previews:** Running `hugo server -D` rebuilds the entire archive in roughly 40 milliseconds on standard hardware.
* **Resilient updates:** Field officers can draft Markdown notices using basic editors without fear of killing the build pipeline due to YAML whitespace or taxonomy rules.
* **Better access:** The interface loads smoothly on low-bandwidth connections across district offices, toggling light and dark palettes automatically while maintaining full text search via Fuse.js.

By stepping away from bloated dynamic environments and investing in modern static architecture, the portal now delivers statutory transparency with virtually zero infrastructure maintenance.
