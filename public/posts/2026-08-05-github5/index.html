GitHub Actions: Complete CI/CD Guide from Beginner to Production#

Writing code is only one part of software development.

Modern software teams automate everything:

  • Building applications
  • Running tests
  • Checking code quality
  • Creating Docker images
  • Publishing releases
  • Deploying applications
  • Sending notifications

GitHub Actions makes all of this possible without leaving GitHub.

Whether you’re building a personal portfolio or managing enterprise software, GitHub Actions helps you deliver software faster, more reliably, and with fewer mistakes.

This guide covers GitHub Actions from the basics to production-ready CI/CD pipelines.

What is CI/CD?#

CI means Continuous Integration.

Developers merge code frequently.

Every change is automatically:

  • Built
  • Tested
  • Verified

CD means:

Continuous Delivery or Continuous Deployment.

Applications are automatically delivered or deployed after successful testing.

What is GitHub Actions?#

GitHub Actions is GitHub’s automation platform.

It executes workflows when specific events occur.

Examples

  • Push code
  • Create Pull Request
  • Open Issue
  • Create Release
  • Schedule task
  • Manual execution

Workflow Structure#

.github/

└── workflows/

    └── build.yml

Every workflow lives inside:

.github/workflows/

Your First Workflow#

Create

.github/workflows/hello.yml

name: Hello World

on:
  push:

jobs:

  hello:

    runs-on: ubuntu-latest

    steps:

      - name: Print Message

        run: echo "Hello GitHub Actions"

Push the file.

GitHub automatically runs it.

Understanding YAML#

Indentation matters.

Correct

name: Build

jobs:

  build:

    runs-on: ubuntu-latest

Incorrect

name:
 Build

Use spaces.

Do not use tabs.

Events (Triggers)#

Run on push

on:
  push:

Run on Pull Request

on:
  pull_request:

Run manually

on:

Run every night

on:

  schedule:

    - cron: "0 2 * * *"

Steps#

Each job contains steps.

steps:

  - run: echo Build

  - run: echo Test

  - run: echo Deploy

Runners#

GitHub executes workflows on runners.

Common runner

runs-on: ubuntu-latest

Other options

windows-latest

macos-latest

Checking Out Code#

Before using project files

steps:

- uses: actions/checkout@v4

This downloads repository contents.

Setting Up Python#

- uses: actions/setup-python@v5

  with:

    python-version: "3.12"

Installing Dependencies#

- run: pip install -r requirements.txt

Running Tests#

- run: pytest

env:

  APP_ENV: production

Use

echo $APP_ENV

Artifacts#

Upload build output

- uses: actions/upload-artifact@v4

  with:

    name: reports

    path: reports/

Download later

actions/download-artifact

Caching Dependencies#

Python example

- uses: actions/cache@v4

  with:

    path: ~/.cache/pip

    key: pip-cache

Benefits

  • Faster builds
  • Lower network usage

Matrix Builds#

Test multiple versions

strategy:

  matrix:

    python-version:

      - "3.10"

      - "3.11"

      - "3.12"

Workflow runs once for each version.

Docker Integration#

Build image

- run: docker build -t app .

Run container

- run: docker run app

Push image

- run: docker push username/app

Building a Python Project#

Example workflow

name: Python CI

on:

  push:

jobs:

  build:

    runs-on: ubuntu-latest

    steps:

    - uses: actions/checkout@v4

    - uses: actions/setup-python@v5

      with:

        python-version: "3.12"

    - run: pip install -r requirements.txt

    - run: pytest

Common Mistakes#

  • Committing secrets
  • Forgetting checkout step
  • Incorrect YAML indentation
  • Hardcoding credentials
  • Running unnecessary jobs
  • Ignoring failed workflows
  • Not caching dependencies

Best Practices#

  • Keep workflows small
  • Cache dependencies
  • Use reusable workflows
  • Store secrets securely
  • Pin action versions
  • Use descriptive job names
  • Test workflows on feature branches
  • Separate build and deploy
