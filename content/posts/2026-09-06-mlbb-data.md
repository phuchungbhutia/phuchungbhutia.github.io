A normal Mobile Legends: Bang Bang build guide usually starts with the hero and ends with a list of recommended items. That approach is useful, but it does not explain **why** those items work. A stronger system starts with the hero's passive and skills, identifies the mechanics that actually produce damage or survivability, maps those mechanics to the required stats, and then finds equipment that amplifies them.

The result is a **mechanics-to-equipment matrix**.

Instead of storing:

```text
Hero → Recommended Build
```

the database can model:

```text
Hero
 ↓
Passive and Skills
 ↓
Scaling
 ↓
Combat Mechanics
 ↓
Required Stats
 ↓
Equipment Effects
 ↓
Synergy Score
 ↓
Recommended Build
```

This approach is particularly useful when building an MLBB hero database, automated build generator, theorycrafting tool, or patch-aware recommendation system.

---

## 1. From Hero Builds to Hero Mechanics

A static build database might contain something like:

| Hero   | Recommended Build                                  |
| ------ | -------------------------------------------------- |
| Thamuz | Corrosion Scythe, War Axe, Oracle                  |
| Eudora | Genius Wand, Holy Crystal, Divine Glaive           |
| Karrie | Demon Hunter Sword, Golden Staff, Corrosion Scythe |

The problem is that this tells us **what** to buy, but not necessarily **why**.

A mechanics-based database instead asks:

* What does the passive scale with?
* Which skill is the primary damage source?
* Does the hero rely on Basic Attacks?
* Does Attack Speed increase the frequency of a passive?
* Does HP contribute to damage?
* Does Defense contribute to damage?
* Does Magic Power affect multiple skills?
* Does the hero benefit from penetration?
* Does the hero depend on cooldown reduction?
* Does healing or regeneration form part of the hero's core combat loop?
* Does an item's passive interact directly with the hero's mechanics?

This produces a much more useful relationship:

```text
Hero
→ Mechanic
→ Scaling
→ Stat
→ Equipment Effect
→ Synergy
```

## 2. The Core Concept: Mechanics-to-Equipment Mapping

The central idea is simple:

> **An equipment item is valuable when its stats or passive effects amplify an important part of the hero's kit.**

Consider a simplified example:

```text
Thamuz
 ↓
Passive generates additional damage through Basic Attacks
 ↓
Attack Speed increases Basic Attack frequency
 ↓
More attacks produce more passive interactions
 ↓
Attack Speed equipment becomes more valuable
```

The database should therefore record the relationship instead of merely recording the item.

For example:

| Hero   | Mechanic              | Scaling         | Equipment        | Synergy   |
| ------ | --------------------- | --------------- | ---------------- | --------- |
| Thamuz | Passive activation    | Attack Speed    | Corrosion Scythe | Excellent |
| Thamuz | Repeated skill damage | Physical Attack | War Axe          | Very Good |
| Thamuz | Sustained combat      | Healing and HP  | Oracle           | Very Good |

This is the foundation of the entire system.

## 4. Why Passive Skills Matter So Much

The passive is often the missing link in conventional build guides.

Two heroes can both deal Physical Damage but benefit from completely different stats because their passives operate differently.

Consider three simplified examples:

```text
Hero A
Passive → Basic Attack
Basic Attack → Attack Speed
Attack Speed → More passive triggers
```

This hero strongly values Attack Speed.

Compare that with:

```text
Hero B
Passive → Skill Damage
Skill Damage → Physical Attack
Physical Attack → Higher burst
```

This hero may prefer Physical Attack and penetration.

And another:

```text
Hero C
Passive → Defense
Defense → Damage
Defense → Survivability
```

For this hero, defensive equipment can have both offensive and defensive value.

That is why the database should treat **passive mechanics as first-class data**.

## 5. Three-Layer Equipment Synergy Model

Equipment should not be categorized only as:

```text
Physical
Magic
Defense
```

That classification is too broad.

A better system uses three layers.

### Layer 1: Statistics

Record the raw statistics supplied by an item.

```text
Physical Attack
Magic Power
HP
Physical Defense
Magic Defense
Attack Speed
Cooldown Reduction
Penetration
Movement Speed
Critical Chance
Lifesteal
Spell Vamp
```

### Layer 2: Combat Mechanics

Identify what those statistics or effects actually improve.

```text
Basic Attack
Skill Damage
True Damage
Critical Damage
On-Hit
Dash
Crowd Control
Shield
Healing
Regeneration
Summon
Clone
Execute
Burn
Mark
Stack
Transformation
```

### Layer 3: Hero Interaction

Finally, connect the equipment to the hero.

```text
Passive → Attack Speed
S1 → Physical Attack
S2 → Cooldown Reduction
Ultimate → Magic Power
Passive → Defense
Ultimate → HP
```

The three layers therefore become:

```text
Equipment
 ↓
Stats
 ↓
Mechanic
 ↓
Hero Interaction
```

## 10. Tank Equipment Is Not Always Purely Defensive

One of the most useful discoveries from this model is that defensive equipment can sometimes increase offensive effectiveness.

Consider:

```text
Defense
 ↓
Hero scaling
 ↓
Damage
```

or:

```text
HP
 ↓
Skill scaling
 ↓
Damage
```

or:

```text
Defense
 ↓
Survivability
 ↓
Longer combat duration
 ↓
More skill cycles
 ↓
Higher total damage
```

This means an item does not need to directly increase Physical Attack or Magic Power to improve a hero's damage output.

### Example

| Hero      | Core Mechanic                    | Offensive Value of Defense |
| --------- | -------------------------------- | -------------------------- |
| Grock     | Defense-based damage             | Direct                     |
| Gatotkaca | Defense and Rage interaction     | Direct and indirect        |
| Belerick  | HP-based retaliation             | Indirect and direct        |
| Hylos     | HP-based resource and damage     | Direct                     |
| Uranus    | Regeneration and extended combat | Indirect                   |
| Edith     | Defense-based transformation     | Direct                     |

This is why the database needs a **mechanics layer** rather than simply an item category.

## 11. Equipment Synergy Scoring

Once the relationships are stored, the system can assign a synergy score.

A simple five-level scale is:

```text
★★★★★ = Excellent
★★★★☆ = Very Good
★★★☆☆ = Good
★★☆☆☆ = Situational
★☆☆☆☆ = Weak
```

For example:

| Hero   | Equipment        | Passive |    S1 |    S2 | Ultimate |   Overall |
| ------ | ---------------- | ------: | ----: | ----: | -------: | --------: |
| Thamuz | Corrosion Scythe |   ★★★★★ | ★★★★☆ | ★★★★☆ |    ★★★★★ | **★★★★★** |
| Thamuz | War Axe          |   ★★★★☆ | ★★★★★ | ★★★★☆ |    ★★★★☆ | **★★★★☆** |
| Thamuz | Oracle           |   ★★★☆☆ | ★★★☆☆ | ★★★☆☆ |    ★★★★★ | **★★★★☆** |
| Thamuz | Blade Armor      |   ★★☆☆☆ | ★☆☆☆☆ | ★☆☆☆☆ |    ★★☆☆☆ | **★★☆☆☆** |

For software implementation, the same rating can be converted into numbers:

```text
★★★★★ = 5.0
★★★★☆ = 4.0
★★★☆☆ = 3.0
★★☆☆☆ = 2.0
★☆☆☆☆ = 1.0
```

The system can then calculate an overall score.

## 12. Weighted Synergy Is Better Than a Simple Score

A five-star score is useful for humans, but an automated build engine needs more detail.

A better formula could be:

```text
Overall Score =
(Passive × Passive Weight)
+
(S1 × S1 Weight)
+
(S2 × S2 Weight)
+
(Ultimate × Ultimate Weight)
+
(Stat Synergy × Stat Weight)
+
(Mechanic Synergy × Mechanic Weight)
```

For example:

```text
Passive Weight   = 25%
S1 Weight        = 15%
S2 Weight        = 15%
Ultimate Weight  = 20%
Stat Synergy     = 15%
Mechanic Synergy = 10%
```

The exact weights should be configurable rather than permanently hard-coded.

This allows different build models:

```text
Burst Build
Sustained DPS Build
Tank Build
Hybrid Build
Anti-Heal Build
Anti-Crit Build
Split-Push Build
Teamfight Build
```

## 17. Keep Hero Data and Item Data Separate

For a larger project, do not put every item definition inside the hero database.

A better architecture is:

```text
MLBB_Database/
│
├── MLBB_Hero_Database.md
├── MLBB_Game_Data.md
├── MLBB_Equipment_Synergy.md
├── MLBB_Build_Logic.md
│
└── data/
    ├── heroes.json
    ├── skills.json
    ├── items.json
    ├── equipment_synergy.json
    └── build_rules.json
```

### `MLBB_Hero_Database.md`

Contains:

```text
Hero
Role
Passive
S1
S2
Ultimate
Scaling
Mechanics
Tags
```

### `MLBB_Game_Data.md`

Contains:

```text
Item
Category
Stats
Unique Passive
Unique Attribute
Effect
Restrictions
```

### `MLBB_Equipment_Synergy.md`

Contains:

```text
Hero
Skill
Mechanic
Required Stat
Equipment
Equipment Type
Synergy Score
Reason
```

### `MLBB_Build_Logic.md`

Contains:

```text
Rules
Weights

```

This also makes patch updates easier. If an item changes, the item definition can be updated without rewriting every hero entry.

## 20. Questions the System Can Answer

Once hero mechanics and equipment data are connected, the database can answer questions that a conventional build table cannot.

### Passive optimization

> Which equipment maximizes this hero's passive?

### Skill optimization

> Which equipment provides the greatest improvement to S1?

### Ultimate optimization

> Which equipment has the strongest interaction with the Ultimate?

### Full-kit optimization

> Which equipment improves the largest number of abilities simultaneously?

### Scaling analysis

> Does this hero benefit more from Physical Attack, Magic Power, Attack Speed, HP, or Defense?

### Hybrid analysis

> Is a hybrid build more efficient than a pure Physical or Magic build?

### Defensive optimization

> Which defensive equipment provides the greatest survivability while preserving offensive output?

### Counter-build analysis

> Which equipment should be selected against the enemy team's damage profile?

### Build generation

## 22. Why This Model Is More Useful

A static database primarily records historical recommendations.

A mechanics-based database records **relationships**.

That distinction is critical.

A recommendation might become outdated after a patch. But if the database stores:

```text
Hero
→ Skill
→ Scaling
→ Mechanic
→ Required Stat
→ Equipment Effect
```

the system can recalculate recommendations when the underlying data changes.

For example:

```text
Item Attack Speed changed
        ↓
Equipment score changes
        ↓
Hero synergy score changes
        ↓
Build ranking changes
```

Likewise:

```text
Hero passive changed
        ↓
Scaling changes
        ↓
Mechanic priority changes
        ↓
Equipment synergy changes
        ↓
Recommended build changes
```

That is much more powerful than manually maintaining hundreds of fixed builds.
